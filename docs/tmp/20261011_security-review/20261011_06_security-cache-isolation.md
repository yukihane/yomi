## 変更内容

content scriptから任意のキーと訳文を指定できた `cache:lookup` / `cache:store` を廃止した。ページ翻訳は原文セグメントの配列・言語・タイトル等の文脈、選択翻訳は原文と言語を渡す構造化要求に変更した。配列の位置が要求内のセグメントIDになる。余分なorigin・キー・訳文等のフィールドを付けた要求は拒否する。

backgroundが命令文とAPI入力を生成し、キャッシュの照合から保存まで行う。キーは形式版、ブラウザー由来のoriginとpathname、言語、モデル、推論設定、高速モード、実際の命令文と文脈、原文をJSON配列にしてハッシュ化する。クエリとfragmentはキーに含めない。命令文が変わればキーも変わる。

ブラウザーのsenderはSPA遷移後も元のURLを返す場合があることをE2Eで確認した。そのため `webNavigation` 権限を追加し、`getFrame` にtabId・frameId・documentIdを渡して現在の文書を照合する。異なるorigin、非activeの文書、文書ID不一致、取得失敗は拒否する。[Chromeの仕様](https://developer.chrome.com/docs/extensions/reference/api/webNavigation#method-getFrame)

1ポート1要求とし、通常の遷移・履歴APIでの遷移・ポート切断で要求をキャンセルする。保存直前にも同じ文書とURLかを再確認し、保存トランザクションにもキャンセルを伝える。新しい要求は新しいポートで受け付ける。

ページ翻訳の応答はバッチ全体を受け取った後、IDの重複・範囲外・不足・不正な形式を確認する。不正なバッチは保存・返却しない。正規のAPI訳文だけを保存し、キャッシュヒットと新しい訳文を同じsegmentイベントで返す。選択翻訳のストリーミングは維持し、選択翻訳とシークレット文書では永続キャッシュの参照・保存を行わない。

## 更新時の動作

- DBをversion 2に更新し、旧行を破棄する。旧APIでは将来の形式に合う任意キーも書けたため、キー形式を変えるだけで旧行を信頼しない。更新後の初回翻訳は再送信・再保存になる。
- 旧設定画面などがDB更新をブロックした場合は、キャッシュを使わず翻訳を続ける。旧画面を閉じて移行が完了した後、次の要求から新DBを使用する。
- 新しいDB接続はversionchange時に閉じる。旧版の開いた画面を新しい接続側から強制的に閉じることはしない。
- 古いcontent scriptの翻訳要求は互換処理で受け付けず、ページ再読み込みを案内する。
- `webNavigation` 権限が増える。用途は翻訳対象文書の確認と遷移時のキャンセルで、閲覧履歴を保存する実装は追加していない。
- ページ翻訳はバッチの全応答を検証するまで表示を待つ。選択翻訳の逐次表示は変わらない。

修正前に、旧キャッシュAPIが任意キーへのアクセスを拒否しない回帰テストの失敗を確認した。最初のE2EではSPAの新しいパスでも旧パスのキャッシュを使うことを検出し、文書照合を追加した別コミットで修正した。

- format、lint、typecheck、buildが成功。
- ユニット: 22ファイル・229件成功。キー条件の分離、旧API拒否、不正なAPI出力の保存拒否、切断後の遅延応答、文書照合、1ポート1要求を検証。
- E2E: 6ファイル・33件成功、2件スキップ。Chrome for Testingで順次実行。
- サイトBの既知キーをサイトAから旧APIで参照・上書きできないこと、origin自己申告の拒否、同一条件の再利用、別originとSPAパスの分離を確認。
- 旧DB接続が移行を妨げても翻訳でき、接続解放後は旧行が消え、正常な再保存と再利用ができることを確認。
- ページ全体・選択翻訳・原文復元・設定画面・#10の権限制御の既存E2Eも成功。

## 残る範囲

同じoriginのcontent scriptが、そのサイトで知っている原文・文脈を使うこと自体は防がない。文脈が本当にDOMにあるかをbackgroundで証明する仕組みではない。返却先の文書と保存先のサイトを分離し、任意の他サイトキーと任意訳文を受け付けないことが今回の境界である。

S3の保存既定無効・7日TTL・手動消去やサインアウトの世代管理は未実装。旧DB破棄とシークレット文書の保存禁止はS4の保存経路統合に合わせて先行したが、S3全体を完了とは扱わない。シークレット条件はユニットで検証し、実際のシークレットウィンドウでのE2Eは未実施。文字数・出力蓄積・全体同時実行数の制限やサイト禁止設定も別対応。

最新mainとの統合では、S1の送信前・応答適用前の原文確認、storage保護の初期化、サインアウトの失効結果返却を維持した。任意キーのキャッシュAPIは再導入せず、backgroundに集約した保存経路を維持する。上記の検証件数は統合前の記録であり、統合後の検証結果はPRに記録する。
