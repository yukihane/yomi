# セキュリティリスクへの対処プラン

- 作成日: 2026-10-11
- 根拠: [調査報告書](20261011_01_security-risks.md)、[再現コード](20261011_02_security-probe.md)、[修正前の証跡](20261011_03_security-probe-result.json)
- 状態: 実装前。今回の成果物は計画のみ。

## 目的と対応順序

意図しない文章の外部送信を最優先で止め、認証情報と保存済み訳文へのアクセスを必要な範囲に限定する。次に保存期間・消去・認証の終了処理を整備する。S1〜S4 を初回の修正リリースの必須対象とし、調査で挙がったその他の改善も以下に割り当てる。

| 順序 | 対象 | 作業単位 | 完了時の状態 |
| --- | --- | --- | --- |
| 1 | S1 | DOM の送信対象判定の統一 | 非表示・除外領域が初回・動的追加・送信待機中とも送信されない |
| 2 | S2、S4 の入口 | 認証 storage とメッセージの認可 | content script から資格情報や拡張画面専用 API にアクセスできない |
| 3 | S4 | キャッシュを background で管理 | 任意サイトのキーや任意訳文を content script が指定できない |
| 4 | S3 | 保存方針・消去と認証終了の連携 | 期限切れを返さず、消去後に旧処理がキャッシュを復活させない |
| 5 | OAuth・負荷上限 | 認証とリクエストの補強 | 不正な callback、失効失敗、過大要求を明示的に扱う |
| 6 | 送信範囲・その他 | サイト設定、説明、最終検証 | 利用者が対象を制御でき、修正前の再現が回帰テストになる |

順序2は順序1と独立して着手可能。順序3は2の呼び出し元情報を利用し、順序4は3で保存処理が集約された後に実装する。順序5の小さな OAuth 修正は先行可能。S1 の修正を、大きなキャッシュ変更の完了まで留め置かない。

## 推奨する製品仕様

以下は本プランで提案する既定値であり、現在の仕様ではない。実装開始時の基準として採用し、変更する場合はテストと説明も揃える。

| 項目 | 提案 |
| --- | --- |
| 永続キャッシュ | 既定は無効。明示的に有効化した場合のみ保存 |
| 保存期限 | 書き込みから7日間。読み取りで延長しない。最大50,000件の件数制限も維持 |
| 消去 | 手動消去、保存無効化、サインアウト、アカウント切り替えで全件消去 |
| シークレットモード | 永続キャッシュの参照・書き込みをともに禁止。通常ウィンドウのキャッシュとも共有しない |
| 旧キャッシュ | 新形式への更新時に破棄。翻訳の再実行が必要になることを更新案内に記載 |
| 除外領域 | `notranslate`、`translate=no`、`hidden`、`aria-hidden=true`、編集領域などを祖先も含めて除外。除外祖先内の明示的な許可で解除しない保守的な方針 |
| 画面外の本文 | ページ全体翻訳の対象として維持し、画面内限定ではないことを説明 |
| タイトル・説明文 | 文脈送信を設定化し、既定は無効。本文とは別に送信されることを説明 |
| サイト制御 | origin 単位で翻訳禁止を設定可能にし、ページ翻訳・選択翻訳・キャッシュの全経路に適用 |

永続キャッシュを無効にすると再訪時の通信・利用枠消費が増える。7日間はセキュリティ仕様が要求する値ではなく、保存の利便性と端末内の残存を両立する提案値。期限は「拡張が動いていない間もその時刻に物理消去する」保証ではなく、期限後は返さず、次回起動・利用時に削除する仕様とする。

## 1. S1: DOM の送信対象判定を統一する

主な変更先: `src/infra/dom/segmenter.ts`、`markup.ts`、`dom-watcher.ts`、`segment.ts`、`src/usecases/content/page-translator.ts`。

1. DOM 依存の判定は `infra/dom` に集約し、明示的な除外と CSS の可視性を分ける。途中の子要素から再走査しても祖先まで判定する。`body` 自体の非表示も例外扱いしない。
2. `checkVisibility` の visibility・opacity 確認を利用する。ただし `display:contents` は自身のボックスがないため、その結果だけで子孫を捨てない。`visibility:hidden` の親に `visibility:visible` の子がある場合は、親の直接テキストを除外しつつ表示される子を走査する。opacity 0 や display none の祖先下は除外する。[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Element/checkVisibility)
3. インライン内の非表示文も直列化から外す。既存の除外要素と同様にプレースホルダー等で元 DOM を保ち、リンク・画像・イベント・原文復元を壊さない。単に DOM から取り除く実装にしない。
4. `translate`、`contenteditable` を含めた属性変更、祖先の属性変更、テキスト変更、追加ノードで関連セグメントを無効化する。現在の `inlineCache` はスタイル変更後も値を保持するため、走査単位のキャッシュにするか適切に破棄する。
5. キャッシュ照合の非同期待機後を含め、実際に翻訳要求を送る直前に対象を再確認する。直列化済みの内容と現在の DOM が食い違えば、そのバッチから外して再走査する。除外されたセグメントには遅れて到着した訳文も適用しない。

修正前に失敗するテストを、非表示のブロック・インライン、`notranslate` / `translate=no` 配下の追加と更新、待機中の祖先の除外指定について追加する。CSS の実際の可視性は Chromium E2E で検証し、DOM モックだけで判定しない。正常系として `display:contents`、表示が復帰した文章、visibility が上書きされた子、画面外の本文、リンクと原文復元を確認する。

完了条件: テスト用の秘密マーカーがモック API の `input` に一度も現れず、通常の翻訳対象は翻訳される。入力欄の値や属性値を新たに収集する変更を入れない。送信後にページが非表示へ変わっても既に送った内容は取り消せないことは残る。

## 2. S2 とメッセージ認可: 信頼境界を明示する

主な変更先: `src/infra/storage/`、`src/infra/messaging/`、`src/usecases/background/`、`src/entrypoints/background/index.ts`、`src/usecases/content/notify-failure.ts`。

`storage.local` を `TRUSTED_CONTEXTS` に制限する初期化を設ける。リスナーは現状どおり同期登録し、認証・メッセージ処理は初期化の Promise を待つ。失敗時は認証や翻訳を開始せず、拡張画面に理由を示す。`storage.session` も信頼されたコンテキストのみに保つ。content script が使う非機密の表示設定は別領域を利用する。[Chrome storage API](https://developer.chrome.com/docs/extensions/reference/api/storage)

既存バージョンが保存した資格情報にも同じ制限を適用する。更新直後に制限適用前の時間帯があり得る点は、旧版からの移行 E2E と API の設定保持挙動で確認する。初期化の待機だけで、既に侵害された旧 content script からの直接読み取りまで遡って防げるとは扱わない。

`onMessage` と翻訳ポートの両方で、ブラウザが与える `sender` を検証する。自拡張 ID の一致だけでは画面と content script を区別できない。拡張画面は自拡張 URL と許可したページパス、content script は HTTP(S) origin・URL と tab/frame/document の情報を検証する。不明な送信元、opaque origin、対象外スキームは拒否する。[Chrome MessageSender](https://developer.chrome.com/docs/extensions/reference/api/runtime#type-MessageSender)

| 操作 | 許可する呼び出し元 |
| --- | --- |
| 認証状態・メール取得、サインイン、サインアウト、モデル一覧、キャッシュ管理 | 自拡張の popup / options |
| ページ・選択翻訳、限定したキャッシュ照合 | 検証済みの content script。認証・サイト方針も別途確認 |
| 設定・使用量画面を開く | 必要な拡張画面と content script。固定の遷移先のみ、連打抑制あり |
| ショートカット設定を開く | 自拡張の popup / options |

現在 `notify-failure.ts` は content script から `auth:signIn` を呼ぶため、「設定を開いてサインイン」へ誘導を変更する。`auth:getState` に含まれるメールを content script に公開しない。popup / options の `credentialsItem.watch` は信頼された画面でのみ使われることを確認する。

呼び出し元の抽出・検証は `infra`、権限と用途の規則は `domain`、認可後の処理は `usecases` に置く。境界スキーマと型は `domain` へ整理し、`BACKGROUND_API` にはエンドポイントの定義を残す。`entrypoints` に認可ロジックを増やさない。

完了条件: content script の `storage.local.get` と変更通知からダミートークンを取得できない。認証専用 API も拒否される。設定画面のサインインと更新・再起動後の翻訳は成功する。送信元不足や権限エラーは、生のトークン・本文をログやエラーに含めない。

## 3. S4: サイトと翻訳要求に紐づくキャッシュに変更する

主な変更先: `src/domain/translation-cache.ts`、翻訳要求のスキーマ、`src/infra/messaging/`、`src/infra/storage/translation-cache.ts`、`src/usecases/background/translate.ts`、`src/usecases/content/page-translator.ts`。

1. `cache:lookup` に完成済みキーを渡す API をやめる。言語と原文セグメントなどの構造化入力を受け、サイト部分は検証済み sender から background が決める。origin を必須の分離境界とし、pathname もブラウザ由来の URL から取得する。クエリやフラグメントを省く現仕様は維持する。
2. ページ翻訳要求をセグメント ID・原文・必要な文脈を持つ型に変更する。命令文の生成とバッチエンコードは background 側の usecase で行う。選択翻訳は別の要求種別にして、永続保存を行わない。
3. content script から任意の訳文を書ける `cache:store` を廃止する。background が、自分で受け取った API の訳文を要求内のセグメントと対応付けて保存する。既存のバッチデコーダーを共有し、不正・不明・重複 ID の訳文を保存しない。返却イベントもキャッシュヒットと新規訳文を同じ形式で扱う。
4. キーには形式バージョン、サイト、言語、原文に加え、訳文に影響するモデル・プロンプト版・使用した文脈を反映する。改行連結の曖昧さを避ける正規化済み構造からハッシュを計算する。
5. メッセージ受付時に文書情報を固定し、別文書への遷移やポート切断でキャンセルする。SPA の URL 変更を含め、古いポートの URL と新しい要求の文脈が混ざらないよう、必要に応じて接続を作り直す。安全に同定できない文書はキャッシュを使用しない。

`sender.url` はフレームの URL を示すため、単純に「現在アクティブなタブ」の URL へ置き換えない。同一 origin 内の侵害された content script が読める原文まで秘密にする仕組みではなく、サイト間の分離と任意保存の禁止を保証対象にする。

完了条件: サイト A から B の既知キーを指定しても B の訳文が返らず、B の値を上書きできない。旧 `cache:store` は拒否される。同じサイト・同じ条件での正常なヒットは維持される。旧拡張の content script は緩い互換経路で受け付けず、再読み込みへ誘導する。

## 4. S3: 保存と消去のライフサイクルを管理する

主な変更先: `src/domain/settings.ts`、`src/domain/translation-cache.ts`、`src/infra/storage/translation-cache.ts`、`src/usecases/background/`、`src/ui/options/CacheSection.tsx`、`AccountSection.tsx`。

キャッシュ行に `createdAt`・`expiresAt` を追加し、期限判定を `domain` で行う。参照・件数取得・起動時の整理で期限切れを除外し削除する。利用時刻は件数超過時の削除順にだけ使う。保存を無効にした時点で既存データも消す。

DB のバージョンを上げ、旧行は一括破棄する。ハッシュ済みの旧キーからサイトや作成日時を復元する移行は行わない。別の拡張画面が DB を開いていて upgrade が止まる場合を処理し、移行完了までキャッシュへアクセスさせない。

現在の `CacheSection` にある直接 IndexedDB 操作を background の管理 API に移す。手動消去、設定変更、サインアウトによる消去を共通の usecase に統一する。

消去処理は次の順序で設計する。

1. 新しい翻訳・キャッシュ処理の受付を止め、実行世代を進める。
2. 進行中の要求をキャンセルし、古い世代の遅延結果と書き込みを失効させる。
3. DB の世代更新と消去をトランザクションで直列化する。書き込みも同じ保存済み世代を確認し、確認と書き込みの間に消去が割り込める実装にしない。
4. サインアウトではローカル資格情報と進行中のサインイン状態も無効化する。遅れて完了した OAuth / refresh が再保存しないよう世代管理を揃える。遠隔失効の通信完了待ちでローカル消去を止めない。
5. 成否を UI へ返す。キャッシュの消去に失敗した場合は「消去済み」と表示せず、キャッシュ利用を停止して再試行できる状態にする。

service worker の停止・再起動をまたぐため、キャッシュの世代はメモリだけに置かない。起動時に新しい実行世代を発行し、旧ポートからの遅延保存を受け付けない。消去後に新たに開始した翻訳の保存は、保存設定が有効なら許可する。

完了条件: 保存無効・シークレットモードでは既存行も返さない。期限境界、手動消去、サインアウト中の遅延応答、アカウント切り替え、worker 再起動、DB 失敗を検証する。サインアウト後に7件が残った修正前ケースは0件になり、遅延応答を解放しても復活しない。

同じ端末に鍵を保存するだけの独自暗号化は今回導入しない。保存最小化と期間制限を先に実施し、OS / プロファイル自体の侵害への完全な防御は保証しない。

## 5. OAuth と過大要求への補強

| 対象 | 実装内容 | 回帰テスト・完了条件 |
| --- | --- | --- |
| callback 判定 | URL を構文解析し、scheme・host・port・pathname を一致確認。user info や予期しない fragment は拒否。state と認可タブ照合は維持 | `/callback-extra`、別ポート、偽ホスト、不正 URL、state 不一致を拒否し、正規 callback は成功 |
| トークンの失効 | HTTP 成否とタイムアウトを処理し、ローカル消去と遠隔失効の結果を分けて返す。通信エラーを認証情報込みで表示しない | 2xx、4xx、5xx、通信断・遅延をモックし、失敗時もローカル消去が完了する |
| refresh と signOut の競合 | 進行中の更新の扱い、更新後トークンの失効、待機の上限を定義。遅い callback も無効化 | サインアウト後に資格情報が復活しない。遠隔失効できなかった場合は成功と表示しない |
| 文字数・件数 | 要求種別ごとの上限を domain のスキーマに定義し、background でも検証。選択文8,000文字、ページ25セグメントを基準にする | 境界値と超過を検証。現 `packBatch` は単独の長文を2,000文字超でも通すため、長文の安全な分割または明示的拒否も同時に実装 |
| 同時実行・連打 | 1ポート1要求。文書ごとの同時実行を現ページ翻訳の4件に合わせ、全体上限・有限キュー・タイムアウトを追加。画面を開く操作も抑制 | 重複要求、大量接続、切断後の要求で枠とタイマーが残らない。複数タブの正常利用も動く |

上限値は実装時に既存の長文・選択翻訳・複数タブのテストから決定し、入力、出力、蓄積するストリームの全てに有限の上限を設ける。超過分を黙って切り捨てたり、無制限に待機列へ入れたりしない。

失効失敗への自動再試行は短時間・有限回とし、再試行のためにサインアウト後のトークンを永続保持しない。遠隔失効の結果は実アカウントでの無断試験ではなくモックで確認し、実サービスとの互換性確認は別の検証項目として残す。

ID トークンの完全な検証は別作業とする。公式仕様に基づき issuer・audience・有効期限・署名と鍵の取得方法を確認してから、実績ある検証実装の採用を判断する。JWT を自作で検証しない。確認が済むまでは nonce と表示用情報以外へ利用を拡大せず、この項目を「解決済み」にしない。S1〜S4 の修正をこの調査の完了には依存させない。

## 6. サイト方針、説明と残る項目

サイト除外設定は origin を正規化して保存する。閲覧先を他端末へ同期する必要がないため、除外リストは保護された `storage.local` に置き、content script へは当該サイトの可否だけ返す。background で翻訳開始・キャッシュ参照・保存を止め、UI の無効化だけに依存しない。設定変更時は対象サイトの進行中の要求もキャンセルする。

README と設定画面に、本文、画面外・追加文章、任意のタイトル・説明文が OpenAI に送られること、キャッシュの保存・消去条件を記載する。「store: false なので一切保持されない」とは表示しない。初回利用時の説明と、禁止サイトでの拒否理由は日本語にする。

プロンプト注入は、ページ文脈を命令と混同しない入力形式・文脈の最小化・出力 ID の検証で影響を抑える。モデルが必ず翻訳指示に従う保証とはしない。任意 HTML の挿入や、モデルによる任意 URL の取得を導入しない。外部から得た文字列で新しいリンク先・イベント属性を生成しない。

供給網対策は既存の lock・待機期間・Actions 固定を維持し、リリース時に依存監査を再実行する。実際の Actions ロック適用と、配布 zip が修正済みコミットから生成されることを確認する。既知脆弱性0件だけで完了と判断しない。

## テストと実装の進め方

各修正では、まず現状で失敗する回帰テストを追加して失敗理由を確認する。単発の監査スクリプトはそのまま製品テストにコピーせず、既存の E2E fixture と型定義を使って `e2e/` に組み込む。設定は `vitest.config.ts` の既存プロジェクトを使い、非同期の結果は `expect.poll` 等で待つ。

ユニットテストは対象と同じ場所に置き、URL・権限・期限・上限・世代遷移の純粋な規則を検証する。ブラウザ E2E は CSS 可視性、content script からの実際の storage / メッセージアクセス、IndexedDB 移行、worker 再起動、画面遷移を検証する。API はモックし、ダミー資格情報以外を使わない。

負の条件は、単に「すぐには送られなかった」では合格にしない。正常な制御用セグメントの処理完了やキュー排出を待ってから全リクエストを検査する。競合テストは応答を明示的に保留し、消去後に解放して確認する。

作業単位ごとに実装をコミットし、その後 `pnpm format`、`pnpm lint`、`pnpm typecheck`、`pnpm test` を実行する。失敗時の修正を別コミットに残す。翻訳・UI に触れる単位は `pnpm build` と E2E も実行する。最終的に S1〜S4 を同じ隔離ブラウザで再検証して、修正前後の証跡を比較する。

## リリースの完了条件
